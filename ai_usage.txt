### 3. Що таке `.ebnf` і як він пишеться?
**EBNF (Extended Backus–Naur Form)** — це формальний запис правил синтаксису мови. Це як математична формула мови: все, що дозволяє парсер, описується цими правилами.

Ось базовий синтаксис EBNF:
1. **Правило (продукція)**: `RuleName = Expression ;`
2. **Термінали** (фіксовані токени/слова/емодзі): пишуться в лапках: `"if"`, `"+"`, `"💀"`, `"📦"`
3. **Нетермінали** (інші правила): назви без лапок: `program`, `statement`, `expression`
4. **Вибір (альтернатива)**: вертикальна риска `|`
   ```ebnf
   type = "📦" | "🏛️" | "💡" ;
   ```
5. **Послідовність**: просто йдуть один за одним:
   ```ebnf
   var_decl = type identifier ":=" expr ;
   ```
6. **Опціональність** (0 або 1 раз): у квадратних дужках `[ ... ]`:
   ```ebnf
   if_stmt = "if" expr "{" stmt_list "}" [ "else" "{" stmt_list "}" ] ;
   ```
7. **Повторення**:
   - `{ ... }` — повторення 0 або більше разів (як `*` у regex).
   - Або якщо 1 і більше: `statement { statement }` (або `statement+`).

```ebnf
(* Declarations: constants (canon), mutable (yap), immutable (canonmaxing) *)
decl         ::= var_kind type ident ":=" expr ;
var_kind     ::= "canon" | "yap" | "canonmaxing" ;

i32_type     ::= "npc"   | "👶" ;
i64_type     ::= "sigma" | "🗿" ;
bool_type    ::= "take"  | "💡" ;

(* Assignment: only allowed for mutable (yap) variables *)
assign       ::= ident ( ":=" | "👈🏻" ) expr ;

(* If-Else block: requires at least one statement in each block *)
if_stmt      ::= "is_this_real" expr "{" statement { statement } "}" [ "nah" "{" statement { statement } "}" ] ;

exit_stmt    ::= "exit" factor ;

(* Expressions *)
expr         ::= arith [ ( "==" | "!=" | "🤝" | "💔" ) arith ] ;

arith        ::= term { ( "+" | "-" ) term } ;

term         ::= factor { "*" factor } ;

factor       ::= number | "hot" | "cringe" | ident | "(" expr ")" ;
```

### Аналіз граматики на масштабованість, консистентність та зручність

Я провів ретельний компіляторний аудит поточної граматики:

#### 1. Детермінованість та однозначність (LL(1) сумісність) — ✅ Відмінно
- **Оператори (Statements):** Множини перших токенів (`FIRST`) для кожного типу оператора взагалі не перетинаються:
  - `decl` починається з `var_kind` (`canon`, `yap`, `canonmaxing`).
  - `assign` починається з `ident`.
  - `if_stmt` починається з `"is_this_real"`.
  - `exit_stmt` починається з `"exit"`.
- Це означає, що рекурсивний спуск (`peek()` / `eat()`) писатиметься максимально просто: за першим же токеном парсер на 100% знає, яку функцію викликати, без бектрекінгу.

#### 2. Пріоритет та асоціативність операторів — ✅ Відмінно
- Граматика строго розбита на шари:
  $$\text{expr (порівняння)} \rightarrow \text{arith (+, -)} \rightarrow \text{term (*)} \rightarrow \text{factor (число, bool, змінна, дужки)}$$
- Завдяки цьому правило `a + b * c` природно обчислює множення раніше, а `x + 1 == y` порівнює результат після додавання.
- Правило `expr ::= arith [ comp_op arith ]` дозволяє **не більше одного порівняння у виразі**, що захищає від помилок подвійного порівняння.

#### 3. Блоки умовних переходів — ✅ Відмінно
- `statement { statement }` всередині `{ ... }` гарантує обов'язкову наявність хоча б одного оператора у блоці, як вимагає ТЗ (`stmt+`).

* **Які помилки знаходить:** чужі символи, яких немає в абетці мови (наприклад, символ `@`, або одиночна `:` замість `:=`).
* **Результат лексера:** список токенів:
  `[Token(YAP), Token(TYPE_SIGMA), Token(IDENT, "x"), Token(ASSIGN), Token(NUMBER, "5")]`.

---

#### Рівень 2: ПАРСЕР (Синтаксичний аналіз)
* **Що отримує на вхід:** список токенів від лексера (парсер уже НЕ знає ні про які байти чи літери, він оперує готовими токенами).
* **Що він робить:** перевіряє **порядок слів (граматику EBNF)** і будує з них синтаксичне дерево (AST).
* **Аналогія з мовою:** перевірка побудови речення. Якщо сказати: *«Стіл біжить синій ложка»* — кожне слово окремо існує в словнику (лексер пропустив!), але разом вони не утворюють граматичного речення.
* **Які помилки знаходить:** порушення структури граматики (наприклад, пропущена закриваюча дужка `}`, порожній блок `is_this_real { }`, або два числа поспіль `x 👈🏻 10 20`).
* **Результат парсера:** дерево AST (`ProgramNode` $\rightarrow$ `DeclNode` $\rightarrow$ `NumberNode`).

---

#### Рівень 3: СЕМАНТИЧНИЙ АНАЛІЗАТОР (Semantic Checker)
* **Що отримує на вхід:** дерево AST від парсера.
* **Що він робить:** перевіряє **зміст, правила типізації та область видимості**. Зазвичай обходить дерево за допомогою патерну *Visitor*.
* **Аналогія з мовою:** класичний приклад Ноама Хомського: *«Безбарвні зелені ідеї люто сплять»*. Усі слова валідні (лексер ОК), граматика ідеальна: прикметник + іменник + прислівник + дієслово (парсер ОК), але речення абсурдне за змістом (як безбарвне може бути зеленим?).
* **Які помилки знаходить у коді:**
  - Додавання булевого до числа: `hot + 5` (парсер вважає це валідним `expr + expr`, але семантика кричить: не можна додавати `take` до `npc`!).
  - Спроба перезаписати константу: оголосили `canon npc x 👈🏻 10`, а потім написали `x 👈🏻 20` (парсер бачить валідне присвоєння, а семантик знає: `x` — константа!).
  - Використання змінної, яку ще не оголосили.
* **Результат:** перевірене дерево, де кожен вузол знає свій тип (`Decorated AST`).

---

#### Рівень 4: КОДОГЕНЕРАТОР (Code Generator)
* **Що отримує на вхід:** декороване AST.
* **Що він робить:** більше нічого не перевіряє, він просто сліпо транслює вузли дерева в низькорівневі команди (у нашому випадку — в LLVM IR: `alloca`, `store`, `load`, `add`, `call @printf`).
* **Результат:** `.ll` файл, який далі збирається у виконуваний двійковий файл (`.exe` / ELF).

---

### Підсумкова шпаргалка:
| Рівень | Вхід | Питання, яке вирішує рівень | Що видає |
|---|---|---|---|
| **Lexer** | Текст (символи) | *«Чи є такі символи і слова в мові?»* | Список токенів |
| **Parser** | Токени | *«Чи правильний порядок слів за граматикою EBNF?»* | Дерево AST |
| **Semantic** | Дерево AST | *«Чи збігаються типи та правила логіки?»* | Типізоване AST |
| **CodeGen** | Типізоване AST | *«Як це записати командами процесора?»* | LLVM IR / Бінарник |
