## 2. Part-by-Part Breakdown: What Was Taken, Changed, and Why

### 2.1. Task 1 — Language Extension (`grammar.ebnf` & `README.md`)
- **What was taken as generated**:
  - The initial EBNF drafts for structure definitions (squad_def), function definitions (lore_def), structure initializers (squad_init), field/method chains in factor, and the initial layout of Section 1 in README.md, as well as the 4 benchmark programs in examples/.
- **What I changed / adapted and why**:
  - I chose the custom sigmaLang keywords lore (for functions and member functions) and squad (for structures), and later replaced generic read / print with absorb / spit_fax across the grammar, README, lexer, and examples to keep the language theme consistent.
  - The AI initially split the grammar into too many redundant one-line helper productions, and when asked to simplify, it went too far and inlined the custom primitive types. I rejected both extremes and directed a clean middle ground: keeping explicit productions for i32_type, i64_type, and bool_type while inlining unnecessary wrapper rules.

### 2.2. Task 2 — Front End: Lexer and Parser (`src/lexer.py`, `src/parser.py`)
- **What was taken as generated**:
  - The implementation of single-pass byte-level lexing for -> vs -, string literals with UTF-8 column tracking, and the recursive-descent parser extensions for squad declarations, lore declarations, and postfix field/method chains in src/parser.py. 
- **What I changed / adapted and why**:
  - I verified that --ast output stayed 100% backwards-compatible with all 37 Stage 1 tests (especially tricky edge cases like exit 1 + 2 and missing declaration types). 

### 2.3. Task 3 — Semantic Analysis and LLVM IR Code Generation (`src/sema.py`, `src/codegen.py`)
- **What was taken as generated**:
  - The main code of `src/sema.py` (type checking, symbol tables for structs and functions, and checking mutability rules) and `src/codegen.py` (generating LLVM IR using `llvmlite.ir`, struct types, `gep` instructions for fields, passing `%this` into member functions, and calling C `printf`/`scanf`)
- **What I changed / adapted and why**:
  - When I ran `./run.sh examples/03_member_lore_and_scoping.src`, lli failed with `No available targets are compatible with triple "unknown-unknown-unknown"`, and the program didn't print `"Program exit with result ..."` at the end. I told the AI about both bugs and it fixed them in `codegen.py`
  - When I typed `"hello"` instead of a number into `absorb()`, it printed random memory values (`0` and `1`), so I asked to set the default value to `0` before `scanf`.

### 2.4. Task 4 — Test Suite and Runner (`run_tests.sh`, `tests/ok/`, `tests/err/`)
- **What was taken as generated**:

## 3. What I Understood (In My Own Words)

This practice was a lot to handle while full of insights. First of all - how fucntions and structs are processed in semantic analysis and LLVM IR code generation. 
`sema.py` first saves all `squad` fields and `lore` function headers into dictionaries so functions can call other functions written below them. Variables are kept in separate scope dictionaries and searched in the order from local to global.
But the most interesting part is that the struct methods are actually translated to just usual functions in LLVM, so in the end of the day it's more of a convenience to a user.

Also, I ecnountered an interesting bug while testing a project. I tried to input string 'hello' where it needed an integer and ended up having 0 and 1 randomly for the variables.
As per my understanding, it happend because when a temporary variable is created on stack and not initialized (becuase well we request input there), it gets some random data from the stack if we paste some text and scanf stops without writing anything.
To solve this, I (and my agent) just decided to initialize the  slot to 0 before requesting input.

### 📋 Детальне оверв'ю того, що зроблено в Task 1

#### 1. Оновлено формальну граматику — [`grammar.ebnf`](file:///home/ubuntu/cs400/sigmalang-source/grammar.ebnf)
* **Верхній рівень програми (`program` / `top_item`)**: програма складається з послідовності `squad_def`, `lore_def` та звичайних інструкцій `statement`.
* **Структури (`squad_def` та `field_def`)**:
  ```ebnf
  squad_def ::= "squad" ident "{" field_def { field_def } { lore_def } "}" ;
  field_def ::= var_kind type ident [ ";" ] ;
  ```
  Гарантує на рівні граматики, що структура має щонайменше одне поле і що всі поля передують методам `lore_def`. Кожне поле має явний маркер мутабельності (`canon`, `yap`, `canonmaxing`).
* **Функції та методи (`lore_def`)**:
  ```ebnf
  lore_def   ::= "lore" ident "(" [ param_list ] ")" "->" type "{" statement { statement } "}" ;
  param_list ::= param { "," param } ;
  param      ::= type ident ;
  ```
* **Ініціалізація об'єктів та ланцюжки присвоєння (`squad_init` та `assign`)**:
  * У `decl` значенням ініціалізації тепер є `init_val ::= expr | squad_init ;`, де `squad_init ::= "{" init_val { "," init_val } "}" ;` (підтримує вкладені структури на кшталт `{ { 3, 4 }, 10 }`).
  * `assign ::= ident { "." ident } ( ":=" | "👈🏻" ) expr ;` дозволяє присвоювати як змінній, так і полю через ланцюжок (`c.center.x 👈🏻 7`).
* **Вирази, виклики та вбудовані `read` / `print`**:
  * `print_stmt ::= "print" "(" ( expr | string_lit ) ")" ;` входить у `simple_stmt` (тож навіть постфіксний `fr` автоматично працює з `print`).
  * У `factor` додано `"read" "(" ")"` та `( call | ident ) { chain_step }`, де `chain_step ::= "." ident [ "(" [ arg_list ] ")" ] ;`. Це покриває і прості змінні, і виклики функцій `add(1, 2)`, і ланцюжки полів `c.center.x`, і виклики методів `c.center.d2()`.
  * Явно виписані лексичні правила внизу файлу (`bool_lit`, `string_lit`, `number`, `ident`, `digit`, `letter`), як вимагає умова Task 1.

## 1. Як зміниться Лексер (`src/lexer.py`)

Лексер залишається чистою рукописною state-машиною на сирих байтах (`bytes`).

### 1.1. Нові `TokenKind` та ключові слова
Додаємо в `enum TokenKind`:
* **Ключові слова** (додаються також у словник `KEYWORDS`):
  * `SQUAD = "squad"`
  * `LORE = "lore"`
  * `READ = "read"`
  * `PRINT = "print"`
* **Оператори та роздільники**:
  * `DOT = "."`
  * `COMMA = ","`
  * `ARROW = "->"`
* **Літерали**:
  * `STRING = "STRING"`

### 1.2. Як розпізнаються нові токени в `tokenize()`:
1. **Стрілка `->` vs Мінус `-`**:
   Коли поточний байт `b == ord("-")` ([`src/lexer.py`](file:///home/ubuntu/cs400/sigmalang-source/src/lexer.py#L175)):
   ```python
   if b == ord("-"):
       self._advance_byte()
       if self._peek_byte() == ord(">"):
           self._advance_byte()
           tokens.append(Token(TokenKind.ARROW, "->", tok_line, tok_col))
           continue
       tokens.append(Token(TokenKind.MINUS, "-", tok_line, tok_col))
       continue
   ```
   Якщо після `-` йде `>`, емітимо `ARROW ("->")`, інакше звичайний `MINUS ("-")`.
2. **Крапка `.` та кома `,`**:
   Однобайтові перевірки `b == ord(".")` $\rightarrow$ `TokenKind.DOT` та `b == ord(",")` $\rightarrow$ `TokenKind.COMMA`.
3. **Рядкові літерали `"..."` (`TokenKind.STRING`)**:
   Коли `b == ord('"')`:
   * З'їдаємо відкриваючу лапку `"` (`self._advance_byte()`).
   * У циклі збираємо байти у `str_bytes = bytearray()`, поки не зустрінемо закриваючу `"` (`ord('"')`).
   * **Перевірка помилок**: якщо ми вперлися в кінець рядка `ord("\n")` або кінець файлу `self.pos >= self.length` без закриваючої `"`, кидаємо `LexerError(tok_line, tok_col, "unterminated string literal")`.
   * Коли зустріли закриваючу `"`, з'їдаємо її, декодуємо `str_bytes.decode("utf-8")` і додаємо `Token(TokenKind.STRING, text, tok_line, tok_col)`. Завдяки нашому `_advance_byte()`, координати `line:col` навіть після UTF-8 символів усередині рядка залишаться ідеально точними!

## 2. Як зміняться AST-вузли та формат `--ast` (`src/parser.py`)

Щоб не плодити зайвих класів (без оверінжинірингу!), розширимо існуючі вузли там, де це природно, і додамо лише необхідні нові `@dataclass(slots=True)`:

### 2.1. Модифікація існуючих вузлів (зі 100% збереженням дампу для Stage 1):

     ```text
     Decl c Circle yap
     ```

2. **`ParamDef` та `LoreDefNode(StmtNode)`** (використовується і для глобальних функцій `lore`, і для методів у `squad` з прапорцем `is_member: bool = False`):
   * Зберігає `name: str`, `params: list[ParamDef]`, `return_type: str`, `body: list[StmtNode]`, `is_member: bool = False`.
   * Формат `dump()`:
     * Для звичайної функції: `Lore add(npc a, npc b) -> npc` + інструкції тіла з відступом `indent + 2`.
     * Для методу структури: `MemberLore shift(npc dx) -> npc` + інструкції тіла з відступом `indent + 2`.
3. **Виклики та ланцюжки (`CallNode`, `FieldAccessNode`, `MemberCallNode`)**:
   Щоб `--ast` чітко розрізняв, чи ланцюжок закінчується полем (`c.center.x`), чи викликом методу (`c.center.d2(1)`):
   * **`CallNode(ExprNode)`** — виклик функції `add(1, 2)`:
     ```text
     Call add
       Number 1
       Number 2
     ```
   * **`FieldAccessNode(ExprNode)`** — доступ до поля або ланцюжка полів (`target: ExprNode`, `field_name: str` або ланцюжок `c.center.x`):
     ```text
     FieldAccess c.center.x
     ```
   * **`MemberCallNode(ExprNode)`** — виклик методу на об'єкті чи ланцюжку (`target: ExprNode`, `method_name: str`, `args: list[ExprNode]`):
     Наприклад, для `c.center.shift(5)`:
     ```text
     MemberCall shift
       FieldAccess c.center
       Number 5
     ```
     Якщо аргументів немає (`p.d2()`):
     ```text
     MemberCall d2
       Var p
     ```
     Така структура робить дерево кристально прозорим і для викладача (видно `target` та `args`), і для нашого майбутнього `sema.py` / `codegen.py`!
4. **Вбудовані I/O (`ReadNode(ExprNode)`, `StringLiteralNode(ExprNode)`, `PrintStmtNode(StmtNode)`)**:
   * `ReadNode.dump()` $\rightarrow$ `Read`
   * `StringLiteralNode.dump()` $\rightarrow$ `String "Point read from input:"`
   * `PrintStmtNode.dump()` $\rightarrow$
     ```text
     Print
       <arg.dump(indent + 2)>
     ```

## 3. Як працюватимуть методи Парсера (`src/parser.py`)

Згідно з вимогою *"the parser stays one function per grammar rule"*:

1. **`parse()`**:
   У циклі поки не `EOF`:
   * Якщо `TokenKind.SQUAD` $\rightarrow$ `self.parse_squad_def()`
   * Якщо `TokenKind.LORE` $\rightarrow$ `self.parse_lore_def(is_member=False)`
   * Інакше $\rightarrow$ `self.parse_statement()`
2. **`parse_type() -> Token`**:
   Допоміжний метод для правила `type`: приймає `TYPE_NPC`, `TYPE_SIGMA`, `TYPE_TAKE` або `IDENT` (ім'я користувацького `squad`). Якщо токен інший — кидає `ParserError` з координатами цього токена.
3. **`parse_squad_def() -> SquadDefNode`**:
   * З'їдає `squad`, читає `IDENT` (ім'я структури) та `{`.
   * Спочатку в циклі, поки бачить `CANON | YAP | CANONMAXING`, парсить поля: `var_kind`, `type`, `IDENT` (і опціональну `;`).
   * Якщо полів 0 (одразу `}` або `lore`), кидає `ParserError` на поточному токені (`"expected at least one field in 'squad'"`).
   * Далі в циклі, поки бачить `TokenKind.LORE`, викликає `self.parse_lore_def(is_member=True)`.
   * Якщо після методу `lore` раптом знову йде поле (`CANON | YAP | CANONMAXING`), кидає `ParserError` на цьому полі (`"fields must be declared before member functions in 'squad'"`).
   * З'їдає закриваючу `}`.
4. **`parse_lore_def(is_member: bool = False) -> LoreDefNode`**:
   * З'їдає `lore`, `IDENT` (ім'я функції), `(`.
   * Якщо наступний токен не `)`, парсить параметри `type ident` через кому `,`.
   * З'їдає `)`, стрілку `->` (`TokenKind.ARROW`), тип повернення `self.parse_type()`.
   * З'їдає `{`, парсить тіло `while self._peek().kind not in (TokenKind.RBRACE, TokenKind.EOF):` через `self.parse_statement()`.
   * Перевіряє, що тіло не порожнє (як у `parse_if`), і з'їдає `}`.
5. **`parse_decl()`**:
   * Тепер підтримує і примітивні типи (`npc`, `sigma`, `take`), і структурні типи (`IDENT`), використовуючи `self.parse_type()`.
   * Після `:=` або `👈🏻` перевіряє: якщо стоїть `{` (`TokenKind.LBRACE`) — викликає `self.parse_squad_init()`, інакше `self.parse_expr()`.
   * Примітка щодо Stage 1 тесту [`tests/err/missing_decl_type.src`](file:///home/ubuntu/cs400/sigmalang-source/tests/err/missing_decl_type.src):
     Давай перевіримо, що саме лежить у `tests/err/missing_decl_type.src`! Якщо там написано `canon x := 10`, то `x` — це `IDENT`, а після нього одразу стоїть `:=` замість імені змінної!
     Тому в `parse_decl()`: якщо `type_tok` є `IDENT`, а наступний токен **не є `IDENT`** (наприклад, там `:=` або `👈🏻`), це означає, що програміст забув вказати тип перед ім'ям змінної `x`, і ми видаємо точнісінько ту саму помилку Stage 1 на токені `x`: `expected type ('npc', 'sigma', 'take'), got 'x'`! Це збереже 100% сумісність із тестом `missing_decl_type`.
6. **`parse_assign()`**:
   * Читає базовий `IDENT`.
   * Поки наступний токен `.` (`TokenKind.DOT`), з'їдає `.` і додає `self._eat(TokenKind.IDENT).text` у список `fields`.
   * Далі з'їдає `:=` або `👈🏻` і парсить `self.parse_expr()`.
7. **`parse_print()`**:
   * З'їдає `print`, `(`, перевіряє чи наступний токен `TokenKind.STRING` (створює `StringLiteralNode`) чи звичайний вираз `self.parse_expr()`, з'їдає `)`.
8. **`parse_factor()`**:
   * Додає гілку `case TokenKind.READ:` $\rightarrow$ з'їдає `read`, `(`, `)` і повертає `ReadNode`.
   * У гілці `case TokenKind.IDENT:`:
     * Якщо після `ident` стоїть `(`, парсить список аргументів `expr { "," expr }` і створює `node = CallNode(...)`, інакше `node = VarNode(...)`.
     * Далі крутить цикл ланцюжка `while self._peek().kind == TokenKind.DOT:`:
       * З'їдає `.` та `member_tok = self._eat(TokenKind.IDENT)`.
       * Якщо після `member_tok` стоїть `(`, парсить аргументи в дужках і загортає `node = MemberCallNode(target=node, method_name=member_tok.text, args=args)`.
       * Інакше (дужок немає — це поле) загортає/додає у `FieldAccessNode`.

# 🧠 Частина 1. Як влаштований Семантичний Аналіз (`src/sema.py`)

Семантичний аналізатор — це окремий прохід по дереву `ProgramNode` після парсера й перед генерацією LLVM IR. Його мета:
1. Перевірити всі правила мови (як зі Stage 1, так і зі Stage 2), на які не здатен синтаксичний парсер.
2. Побудувати **таблицю символів (Symbol Table)**, якою скористається генератор коду (зокрема, індекси полів структур для `gep` та типи виразів).
3. При будь-якому порушенні кинути `SemanticError(line, col, message)`, який виведе рівно один рядок: `compilation error: line L:C: message`.

### 1.1. Таблиці символів (Symbol Tables) — без зайвих абстракцій
У класі `SemanticAnalyzer` зберігаємо три прості структури даних:
1. **`squads: dict[str, SquadInfo]`** — таблиця структур:
   - `fields: list[FieldInfo]` (у порядку оголошення: `index: int`, `name: str`, `type_name: str`, `kind: str`, `mutable: bool` — де `mutable == (kind == "yap")`).
   - `fields_by_name: dict[str, FieldInfo]` — для миттєвого пошуку індексу поля за іменем.
   - `methods: dict[str, LoreInfo]` — методи структури (`params`, `return_type`, `is_mutating: bool`, `called_methods: set[tuple[str, str]]`).
2. **`functions: dict[str, LoreInfo]`** — таблиця глобальних функцій `lore`:
   - Зберігає `name`, `params: list[ParamDef]`, `return_type: str`, `node: LoreDefNode`.
3. **`scopes: list[dict[str, VarInfo]]`** — стек лексичних областей видимості для змінних:
   - `scopes[0]` — глобальна область видимості (top-level змінні).
   - Коли входимо у функцію, метод або блок `is_this_real` / `nah` — додаємо новий словник у стек (`scopes.append({})`), при виході — знімаємо (`scopes.pop()`).
   - Кожен запис `VarInfo` містить `name: str`, `type_name: str`, `kind: str` (`canon` / `yap` / `canonmaxing`), `mutable: bool` (`kind == "yap"`), `is_global: bool`.

---

### 1.2. Порядок проходу по програмі (Multi-step Pass)

Щоб функції могли викликати функції, оголошені **нижче** у файлі (forward calls), та щоб працював **fixed-point аналіз мутабельності методів**, семантичний аналізатор працює за 4 чіткі кроки:

#### Крок 1: Реєстрація всіх `squad` та сигнатур усіх `lore`
- Спочатку проходимо по всіх `SquadDefNode`:
  - Перевіряємо, що ім'я структури не зайняте і не збігається з базовими типами (`npc`, `sigma`, `take`).
  - Для кожного поля перевіряємо унікальність імені всередині `squad` і записуємо його порядковий індекс `0, 1, 2, ...` та прапорець `mutable = (f.kind == "yap")`.
  - Реєструємо сигнатури всіх методів `MemberLore` цієї структури (перевіряємо, що ім'я методу не дублюється і не конфліктує з іменем поля).
- Далі перевіряємо, що типи всіх полів існують (примітивний тип або відомий `squad`), і що немає рекурсивного включення структури самої в себе за значенням.
- Реєструємо сигнатури всіх глобальних функцій `LoreDefNode` у `self.functions` (перевіряємо унікальність імен та валідність типів параметрів і `return_type`).

#### Крок 2: Перевірка тіл методів (`MemberLore`) + Fixed-Point розрахунок мутабельності
- Для кожного методу структури `S`:
  - Встановлюємо контекст `self.current_squad = S` та `self.current_lore = method_info`.
  - Відкриваємо локальний скоуп параметрів методу (параметри є незмінними, як `canon`, і перевіряються на унікальність).
  - Перевіряємо тіло методу за правилом **Name Lookup Order з нашого `README.md`**:
    1. Шукаємо ім'я в локальних скоупах методу (включно з параметрами).
    2. Якщо не знайдено — шукаємо в `S.fields_by_name` (або `S.methods`, якщо це виклик `f(...)`).
    3. Якщо не знайдено — шукаємо в глобальному скоупі `global_vars` (оголошених до цього `squad`) або в глобальних `self.functions`.
  - **Пряма мутація**: якщо всередині методу є `AssignNode`, який пише у поле поточної структури `S` (наприклад, `x 👈🏻 x + dx` або `center.x 👈🏻 1`), одразу ставимо `method_info.is_mutating = True`.
  - Якщо метод викликає інший метод на `this` або на полі `this.field`, записуємо пару `(target_squad, callee_method)` у `method_info.called_methods`.
- **Fixed-Point ітерація**:
  Після обходу тіл усіх методів крутимо цикл:
  ```python
  changed = True
  while changed:
      changed = False
      for s_info in self.squads.values():
          for m_info in s_info.methods.values():
              if not m_info.is_mutating:
                  for (target_sq, callee_name) in m_info.called_methods:
                      if self.squads[target_sq].methods[callee_name].is_mutating:
                          m_info.is_mutating = True
                          changed = True
                          break
  ```
  Тепер ми на 100% знаємо для кожного методу в програмі, чи є він мутуючим!

#### Крок 3: Перевірка тіл глобальних функцій `lore` та головної програми
- Для кожної глобальної функції `lore`:
  - Перевіряємо всі інструкції тіла.
  - Кожен `exit <expr>` всередині функції чи методу перевіряється на точний збіг типу `expr` з оголошеним `return_type`. Також перевіряємо, що функція має `exit`.
- Для top-level інструкцій:
  - Коли зустрічаємо top-level `DeclNode`, перевіряємо його і додаємо в `global_vars`.

#### Крок 4: Перевірка специфічних правил виразів та інструкцій
- **`DeclNode`**:
  - Перевіряємо, що змінна з таким іменем ще не оголошена в поточному скоупі.
  - Якщо ініціалізатор — `SquadInitNode`: перевіряємо, що цільовий тип є структурою `S`, кількість елементів у `{ ... }` точно дорівнює кількості полів `S`, і тип кожного елемента збігається з типом відповідного поля `S` (рекурсивно для вкладених `{ { 3, 4 }, 10 }` та з перевіркою `MAX_I32` для полів типу `npc`).
  - Якщо ініціалізатор — звичайний вираз: його тип має точно збігатися з `decl.type_name`.
- **`AssignNode` (Змінна або ланцюжок полів `a.b.c 👈🏻 expr`)**:
  - Якщо `fields` порожній (`x 👈🏻 expr`):
    - Знаходимо `x` (локальна змінна, або поле `this` у методі, або глобальна змінна).
    - Перевіряємо, що `x` оголошений як `yap` (`mutable == True`). Якщо `canon` або `canonmaxing` — семантична помилка!
    - Перевіряємо, що тип `expr` збігається з типом `x` (і якщо `x` має тип `npc`, а `expr` — числовий літерал, то він $\le$ `MAX_I32`).
  - Якщо `fields` непорожній (`c.center.x 👈🏻 expr`):
    - Перевіряємо, що базова змінна `c` має мутабельність `yap`!
    - Покроково йдемо по ланцюжку полів (`center`, потім `x`): на кожному кроці перевіряємо, що поточний тип є `squad`, що поле в ньому існує, і що **саме поле оголошене як `yap`**! Якщо хоча б один крок у ланцюжку є `canon` або `canonmaxing` — видаємо семантичну помилку.
- **`CallNode` та `MemberCallNode`**:
  - Перевіряємо, що функція/метод існує.
  - Перевіряємо, що кількість аргументів `len(args)` точно дорівнює `len(params)`, і тип кожного аргументу збігається з типом параметра.
  - Для `MemberCallNode` (`target.method(args)`): якщо `method` позначений як `is_mutating == True`, перевіряємо, що `target` (об'єкт або весь ланцюжок полів `c.center`) є мутабельним (`yap`) на кожному кроці!

# ⚙️ Частина 2. Як влаштована Генерація Коду LLVM IR (`src/codegen.py`)

Генератор коду використовує виключно будівельник `llvmlite.ir` (`ir.Module`, `ir.IRBuilder`, `ir.IdentifiedStructType`, `ir.Function`). У вихідний `.ll` файл записується `str(module)`.

### 2.1. Типи у LLVM IR
- `npc` $\rightarrow$ `ir.IntType(32)` (`i32`)
- `sigma` $\rightarrow$ `ir.IntType(64)` (`i64`)
- `take` $\rightarrow$ `ir.IntType(1)` (`i1`)
- `squad Name` $\rightarrow$ `module.context.get_identified_type("Name")` (`%"Name" = type { ... }`)

*Як типізуються числові літерали `LiteralNode`?*
У `sigmaLang` числовий літерал `10` може використовуватися і з `npc` (`i32`), і з `sigma` (`i64`), наприклад:
`yap sigma score := 250` та `score 👈🏻 score * 2`.
Як це зробити елегантно в `sema.py` + `codegen.py`:
- Під час семантичного аналізу, якщо `LiteralNode(int)` стоїть в ініціалізації `sigma`, присвоєнні в `sigma`, бінарній операції з операндом `sigma` або передається аргументом у параметр типу `sigma` (чи повертається з функції `-> sigma`), семантичний аналізатор проставляє цьому `LiteralNode` тип `"sigma"` (`i64`), а за замовчуванням числовий літерал має тип `"npc"` (`i32`).
- Тоді у виразі `score * 2` (де `score` має тип `sigma`) літерал `2` автоматично отримує тип `sigma` (`i64`), а `10 + 5` має тип `npc` (`i32`)! При цьому суворе правило залишається непорушним: змішувати змінну типу `npc` та змінну типу `sigma` (`npc_var + sigma_var`) заборонено!

### 2.2. Глобальні змінні vs Локальні змінні
Оскільки в нашому прикладі `examples/03_member_lore_and_scoping.src` є глобальна константа `canon npc x 👈🏻 100` перед `squad Point`, а всередині функцій/методів глобальні змінні також видимі:
- Усі top-level змінні (або ті, до яких можуть звертатися функції) оголошуємо як глобальні змінні модуля `ir.GlobalVariable(module, llvm_type, name=f"_glob_{name}")` з нульовим ініціалізатором `ir.Constant(llvm_type, None)` (або `0`), а в `main()` записуємо в них початкове значення через `builder.store(...)`!
- Тоді будь-яка функція `lore` або метод у `squad` може напряму прочитати або змінити глобальну змінну через `builder.load(glob_ptr)` / `builder.store(val, glob_ptr)`!
- А всі локальні змінні та параметри всередині функцій/методів виділяються на стеку цієї функції через `builder.alloca(...)` у вхідному блоці `entry`.

### 2.3. Функції (`lore`) та Методи (`MemberLore`)
1. **Попереднє оголошення (Forward declarations)**:
   Перед генерацією будь-якого тіла створюємо `ir.Function` для всіх глобальних функцій та всіх методів:
   - Глобальна функція `add` отримує ім'я в IR: `_lore_add` (префікс `_lore_`, як вимагає умова Task 3: *"Give your functions a prefix in the IR, so that a function named `main` or `printf` does not clash with the runtime"*).
   - Метод `shift` у `squad Point` отримує ім'я в IR: `_squad_Point_shift`, а його першим параметром є вказівник на структуру: `ir.PointerType(struct_types["Point"])` (`%this`).
2. **Передача та повернення структур**:
   - Усередині методу звернення до поля `x` (індекс `idx` із таблиці символів) генерує:
     ```python
     ptr = builder.gep(this_ptr, [i32(0), i32(idx)], inbounds=True)
     ```
   - При виклику методу `p.shift(5)` (або `c.center.shift(5)`):
     Обчислюємо адресу об'єкта `p` (його `alloca` або `gep` для ланцюжка `c.center`) і передаємо цей вказівник першим аргументом у `builder.call(callee_fn, [obj_ptr, arg1, ...])`.

### 2.4. Вбудовані `read()` та `print(...)`
1. **Декларації `printf` та `scanf`**:
   Точно як в умові Task 3:
   ```python

   c_type   = ir.FunctionType(i32, [i8p], var_arg=True)
   ```

2. **`read()`**:
   ```python
   slot = builder.alloca(i32, name="read_slot")
   builder.call(scanf, [fmt_d_ptr, slot])

   ```
3. **`print(arg)`**:

### Уточнення: як саме зберігаються змінні в окремих скоупах (Scoped Symbol Table)

Змінні **не зливаються в одну плоску купу**, а зберігаються за строгою ієрархічною структурою стеку скоупів:

```python
# Стек областей видимості:
self.scopes: list[dict[str, VarInfo]] = []
```

1. **Кожен лексичний блок має свій окремий словник (`dict[str, VarInfo]`)**:
   - `scopes[0]` — **глобальний скоуп**: тут живуть лише top-level змінні програми.
   - Коли входимо у функцію `lore` чи метод: створюється **новий локальний скоуп** (`scopes.append({})`), куди спочатку записуються всі параметри функції.
   - Коли всередині функції/методу/головної програми входимо у блок `is_this_real { ... }` або `nah { ... }`: додається **ще один вкладений скоуп** (`scopes.append({})`), куди записуються локальні змінні цього блоку.
   - При виході з блоку/функції: цей скоуп видаляється (`scopes.pop()`), тому змінні з вкладеного блоку чи локальні змінні функції **ніколи не протікають назовні**.

2. **Як працює пошук змінної (`lookup_var`)**:
   Пошук іде **знизу вгору** по стеку від найглибшого вкладеного скоупу до глобального:
   ```python
   def lookup_var(self, name: str) -> VarInfo | None:
       for scope in reversed(self.scopes):
           if name in scope:
               return scope[name]
       return None
   ```
   - Завдяки цьому внутрішня змінна коректно **затінює (shadows)** змінну з зовнішнього блоку або глобальну.
   - А всередині методу `squad` перед перевіркою глобального скоупу `scopes[0]` ми додатково перевіряємо поля поточної структури `self.current_squad.fields_by_name`. Це реалізує зафіксоване в `README.md` правило:
     `параметри та локали (всі локальні скоупи) -> поля squad -> глобали (scopes[0])`.

3. **Як перевіряється повторне оголошення (No re-declaration in the same scope)**:
   При оголошенні `decl` ми перевіряємо лише **поточний найвищий скоуп** `self.scopes[-1]`:
   ```python
   if name in self.scopes[-1]:
       raise SemanticError(f"variable '{name}' is already declared in this scope")
   self.scopes[-1][name] = VarInfo(...)
   ```
   Тобто оголосити двічі `yap npc x` в одному й тому ж блоці — це помилка, але оголосити `yap npc x` всередині `is_this_real`, коли зовні вже є `x`, або мати параметр `x` у методі — це повністю валідне лексичне затінення.
