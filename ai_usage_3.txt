## 2. Part-by-Part Breakdown: What Was Taken, Changed, and Why

### 2.1. Task 1 — Loops (`while`, `for`, `break`)
- **What was taken as generated**:
    - The AST nodes (WhileStmtNode, ForStmtNode, BreakStmtNode), semantic checks for loop scopes and break depth, LLVM IR basic block generation in src/codegen.py, and the 7 loop tests in tests/ok/ and tests/err/.
- **What I changed / adapted and why**:
   - The AI initially proposed grind for while loops, streak for for loops, and ragequit for break. I kept streak and ragequit, but changed the while keyword to as_long_as because it makes much more sense when reading loop conditions.
   - When checking src/lexer.py (lines 31–34), I noticed the AI still kept the plain "while", "for", and "break" strings as the primary TokenKind values instead of our custom keywords. I pointed this out and had it set as_long_as, streak, and ragequit as the main token values while keeping standard keywords as aliases.
   - I also questioned whether the range operator `..` in `streak i in 0 .. 10` would conflict with struct field access `.` in the lexer, and we verified that a 1-byte lookahead cleanly separates `..` from `.`.

### 2.2. Task 2 — The Optimizer (src/optimizer.py, --optimize)
- **What was taken as generated**:
    - The implementation of src/optimizer.py (EffectAnalyzer, UseCounter, Pruner, Inliner, and ASTOptimizer), the --optimize CLI flag handling in compiler.py and run.sh, the 6 optimizer tests in tests/optimizer/, and the before/after LLVM IR comparison in README.md.
- **What I changed / adapted and why**:
    - Instead of letting the AI invent a custom optimizer structure, I told it to base the design on my course practice code (cs400-course-repo-vkatsel/optimizer.py) using separate tree passes that count variable reads (reads) and function calls (fn_calls) in a fixpoint loop
    - I also reviewed the plan and questioned the need for EffectAnalyzer before approving it, to make sure we don't drop unused variable declarations initialized with absorb() or function calls.

### 2.3. Task 3 — The Real Program (programs/sigma_blackjack.txt)
- **What was taken as generated**:
    - The code for programs/sigma_blackjack.txt (BlackjackTable struct with 6 methods, LCG random functions, game loop), the two recorded test sessions (.in and .expected), and the native binary compilation step (llc + clang) in run_tests.sh and README.md.
- **What I changed / adapted and why**:
    - For random card generation, the AI suggested either linking external C rand() in LLVM IR or writing a deterministic LCG generator in sigmaLang. I rejected external C calls as overengineering for this scope and chose the deterministic LCG seeded by user input, which also keeps automated tests 100% reproducible.
    - After testing the program myself, I noticed ./run.sh was auto-feeding the .in file instead of letting me type, and the console output was too cluttered because totals were printed after every card. I asked the AI to remove the auto-fed .in file and print player/dealer totals only at the end of each phase.

### 1. Чи є в LLVM готові цикли, чи це робиться самостійно?

У чистому LLVM IR **немає високорівневих конструкцій типу `while` чи `for`**.  
На рівні LLVM будь-який цикл будується самостійно з **Basic Blocks (базових блоків)** та інструкцій переходів:
* Створюються блоки:
  - `loop.cond` (обчислення та перевірка умови);
  - `loop.body` (тіло циклу);
  - `loop.step` (для `for`: інкремент лічильника діапазону);
  - `loop.exit` (блок виходу з циклу).
* Наприкінці `loop.body` (або `step`) стоїть безумовний перехід назад у `loop.cond` — це і є той самий **back edge** (зворотне ребро), про який прямо написано у вимогах: *"lowered to basic blocks with a back edge"*.
* Умова в `loop.cond` перевіряється через `builder.cbranch(cond, body_bb, exit_bb)`.

Ви у своєму `codegen.py` вже успішно робите це для `is_this_real` (`IfStmtNode`) з `then_bb`, `else_bb`, `merge_bb`. Для циклу логіка майже така сама, тільки з переходом назад!

### 2. Чи можна використати готову частину парсера?

**Так, абсолютно! З нуля нічого писати не треба.**  
* Вирази для умови чи меж діапазону парсяться вже готовим методом `parse_expr()`.
* Тіло циклу `{ statement { statement } }` парситься точно так само, як у вас зараз парситься тіло `if_stmt` чи функцій `lore`.
* Ми лише додаємо нові методи `parse_while_stmt()` та `parse_for_stmt()`, які просто викликають уже готові методи парсингу виразів і списку інструкцій.

Ось детальний розбір та вимоги до оптимізатора за специфікацією:

#### 1. Де і як працює оптимізатор?
- Оптимізатор працює **над AST-деревом після семантичного аналізу (`sema`) і ДО генерації LLVM IR (`codegen`)**.
- Активується новим прапорцем CLI: `--optimize` (може стояти в будь-якому місці аргументів командного рядка):
  - `python3 compiler.py input.txt output.ll --optimize` — оптимізує AST і генерує швидший/чистіший IR.
  - `python3 compiler.py --optimize --ast input.txt` (або `python3 compiler.py --ast --optimize input.txt`) — друкує оптимізоване дерево AST.
- **Головне правило оптимізацій**: програма має виводити **абсолютно однаковий результат** як з `--optimize`, так і без нього. Усі 68 тестів тестового набору мають проходити з увімкненим `--optimize`.

---

#### 2. Три оптимізаційні трансформації AST:

1. **Unused variables (Видалення невикористаних змінних — 1 бал)**:
   - Якщо оголошена змінна ніде не читається, ми видаляємо її `decl` та всі наступні `assign` до неї.
   - Працює **ітеративно до фіксованої точки** (поки є що видаляти: видалення присвоєння може зробити невикористаною іншу змінну).
   - Враховує області видимості (`scopes`) і затінення (`shadowing`).
   - ⚠️ **Критично (Side Effects)**: якщо у виразі присвоєння є виклик функції або введення `absorb()`, сам вираз/виклик **не можна просто викинути**, оскільки він змінює стан або очікує ввід від користувача!

2. **Unused functions (Видалення невикористаних функцій — 1 бал)**:
   - Якщо функцію `lore` ніхто не викликає (ні з `main`, ні з інших функцій чи методів), ми повністю видаляємо її разом із тілом.
   - Працює **ітеративно**: видалення однієї функції може зробити невикористаною іншу допоміжну функцію.

3. **Inlining (Інлайнінг функцій — 2 бали)**:
   - Якщо функція викликається **рівно один раз** у всій програмі:
     - Її тіло підставляється безпосередньо на місце виклику.
     - Параметри стають локальними змінними, ініціалізованими значеннями переданих аргументів.
     - Змінні перейменовуються (alpha-renaming / mangling), щоб їхні імена гарантовано не конфліктували зі змінними зухвалого коду (caller).
     - Результат виходу `exit` стає значенням, яке підставляється замість виклику.
     - Сама функція після цього видаляється як unused.
   - ⚠️ **Обмеження**:
     - Рекурсивні функції **ніколи** не інлайняться.
     - У README чітко описується, які форми ми інлайнимо (наприклад, функції з прямим `exit` без складного дострокового розгалуження).

### Що конкретно робить `EffectAnalyzer`?

Він відповідає на одне просте запитання:  
👉 **«Чи має цей вираз side-effects (побічні ефекти)?»**

Він перевіряє:
1. **Прямі ефекти**:
   - чи є у виразі `absorb()` (введення з терміналу);
   - чи є у виразі друк `spit_fax`;
   - чи є цикли.

# Важливий технічний момент: Генерація випадкових чисел (RNG)
Оскільки в чистому LLVM IR / базовій стандартній бібліотеці `sigmaLang` немає вбудованого `random()`, ми можемо красиво реалізувати класичний **Linear Congruential Generator (LCG)** прямо в `sigmaLang` як окрему функцію або метод структури:
```sigmalang
lore next_random(seed: npc) -> npc {
    # Формула LCG: (a * seed + c) % m
    # Наприклад: (seed * 1103515245 + 12345) % 2147483647
    ...
}
```
* **Плюс для детермінованих тестів (`.in` / `.expected`):** початковий `seed` гравець вводить на старті (або він береться від першої ставки), тому результат повністю детермінований і тести проходитимуть 100% стабільно!

### Варіант 1: Власний чистий PRNG на `sigmaLang` (Лінійний конгруентний генератор — LCG)
Це класичний алгоритм, який використовувався в ранніх версіях C (`rand()`), Java та старих операційних системах. Він реалізується буквально в 3 рядки формулою:
$$X_{n+1} = (a \cdot X_n + c) \pmod m$$

У синтаксисі `sigmaLang`:
```sigmalang
lore next_random(seed: npc) -> npc {
    # a = 1103515245, c = 12345, m = 2147483647 (стандартний ANSI C PRNG)
    # або простіші магічні константи, наприклад a = 1664525, c = 1013904223
    yap npc next_val := (seed * 1103515245 + 12345) % 2147483647;
    if (next_val < 0) {
        next_val := 0 - next_val;
    }
    exit next_val;
}

lore draw_card(seed: npc) -> npc {
    # Отримуємо карту від 2 до 11 (2..10 - звичайні, 10 - валет/дама/король, 11 - туз)
    # Формула: 2 + (rnd % 10)
    yap npc raw := next_random(seed);
    yap npc card := (raw % 10) + 2;
    exit card;
}
```

#### Звідки береться початковий `seed` (зерно рандому)?
1. **Інтерактивно від гравця:** на початку гри програма пише:
   `spit_fax("Enter lucky seed number (any number):");`  
   `table.rng_seed := absorb();`
   Коли гравець вводить будь-яке число (наприклад, свій улюблений номер, день народження чи просто `42`), генератор стартує з нього.
2. **Динамічне оновлення зерна під час гри:**
   Кожного разу, коли гравець робить ставку чи натискає дію (Hit / Stand), ми додатково додаємо його вибір до `seed`:
   `table.rng_seed := table.rng_seed + bet + choice;`
   Завдяки цьому карти ніколи не повторюються однаково, навіть якщо грати багато раундів!
3. **Чому це ідеально для тестів (`.in` / `.expected`):**
   У тесті ми фіксуємо введений `seed` (наприклад, `seed = 777`). Карти випадатимуть у строго детермінованому порядку, тому файл `.expected` буде на 100% стабільним і тест ніколи не "блиматиме" (flaky test).

---

### Варіант 2: Додати зовнішній виклик C-функції `rand()` через LLVM IR
Оскільки наш компілятор генерує нативний бінарник через `clang`, ми технічно можемо оголосити зовнішній `declare i32 @rand()` (або `time()`) в рантаймі.
**Але:** для автоматичних тестів (`run_tests.sh`) справжній недетермінований `time(NULL)` створить проблему — вивід гри кожного запуску буде іншим, і звичайний `diff programs/NAME.expected programs/NAME.out` впаде!

Тому **Варіант 1 (LCG прямо в коді `sigmaLang`)** — це ідеальне рішення:
- По-перше, викладач бачить, що ви написали алгоритмічний PRNG на власній мові програмування (за це окремий респект).
- По-друге, він повністю детермінований для тестів за умови фіксованого стартового `seed`.
- По-третє, у грі це відчувається як справжній рандом.

### 3. Чому тести пройшли?
